### 0.2 全局约定

- **后端地址**：默认 `http://127.0.0.1:9090`，API 前缀 `/api/v1`；环境变量 `BACKEND_URL` 可覆盖。
- **Core 地址**：默认 `http://127.0.0.1:8080`；环境变量 `CORE_URL` 可覆盖。
- **返回值契约**：统一 `ApiResponse<T>{ code, message, data }`，**`code === 0` 视为业务成功**（与前端 `client.js` 拦截器一致）。断言一律基于 `code`/`data`，杜绝「接口存在即通过」。
- **断言原则**：每条用例必须有可验证断言点（字段存在性 / 结构 / 数值范围 / 状态机跃迁 / 计数）。无法纯 API 验证的项（Collector 内部采样、前端渲染）给出「人工/日志核查步骤 + 断言口径」，不假通过（见 §5）。
- **T-L 边界字段口径**（来自详细设计 §3.3③）：每个洞察 VO 含 `boundary ∈ {L1,L2,L3}`、`confidence`（仅 L2 有，∈[0,1]，L1/L3 为 `null`）、`requiresApproval`（bool，L3 默认 true，其余 false）、`autoExecutable`（全局 false）。

### 0.3 通过标准（本轮验收 gate）

1. 所有必做任务（T-A~T-I）的脚本用例执行 **FAIL = 0**；
2. @Scheduled 求值、抑制、状态机（FIRING→ACKED→RESOLVED）均有真实事件佐证；
3. 分页 `totalElements/totalPages` 正确、大 offset 不 OOM、排序稳定；
4. T30 死 key 删除后主指标 API 不回归（insights/accuracy 仍返回真实数据）；
5. Collector `otelcol validate` 通过且健康检查 Span 不入 Backend；
6. 可选任务（T-J~T-N）至少完成「契约/代码核查 + 可 API 验证部分」；无 API 暴露的部分以人工核查步骤闭环。

## 1. 测试数据准备（如何 seed / 构造触发条件）

### 1.1 后端种子数据（已有脚本，直接复用）

```bash

```

`seed_all.py` 覆盖 36 轮对话（转账/账单/理财/基金等），产生：
- `sessions` / `session_turns` 多会话（约 15 个 distinct sessionId，含 `zs1/zs2/ww1/np1..np5`）；
- `spans`（经 Collector 入 Backend，含 L0/L1/L2 分层意图 span）；
- `metrics_agg`（request_count / error_count / token / ttft 等），为 T-A 交叉分析、T-D 分页、T-E 主指标回归提供真值。

### 1.2 告警异常触发（T-B/T-F 专用）

默认 5 条规则阈值较严，未必被种子流量自然触发。测试脚本采用**确定性注入**：
- 通过 `POST /api/v1/alerts/rules` 创建一条「`metricKey=REQUEST_COUNT_ASSUMPTION` operator='>' threshold=0」的规则（种子后 `request_count>0` 必然成立 → 下一求值周期必 FIRING）。
- 注入前先确认 `collectMetricValue` 的 metricKey 映射（见 §2.2 假设表），默认按 Redis key `request_count` 推导；若引擎实际 key 不同，用例**明确失败**（不假通过），需与工程师对齐。
- 抑制窗口 = 300s（Redis `obs:alerts:suppress:{ruleId}` TTL），状态机 `FIRING→ACKED`（POST `ack`）→`RESOLVED`（指标恢复后下一周期）。

### 1.3 死 key / 注册表 / 提示词 / reRoute 构造

- **T-E**：依赖 T30 已删除 `RedisH2SyncService` 中 5 行 `addDoubleGauge`；种子后等 30s 让同步逻辑跑过，主指标 API 应仍正常。H2 直查 `redis_metrics_snapshot` 表验证 5 行缺失（人工/脚本 SQL）。
- **T-J/T-K**：依赖 Core 侧 `MetricsRegistry` + `AddUpDown` 埋点；后端若暴露 actuator metrics（`/actuator/prometheus`、`/actuator/metrics`）则断言 `deepflux.*` 前缀指标存在。
- **T-M**：通过 prompt-versions API 建版本 + 激活，断言版本单调性 + ACTIVE 最大版本。
- **T-N**：通过 `POST /api/v1/sessions` 直接模拟 `SessionBridge` 上报（body 带 `reRouted:true, originalQuery:"..."`），断言落库后 `rerouteTriggered=true` 且 `toTurnVO` 不再硬编码 false。

## 10. 与 verify-E2E.sh 的协同（C 部分要求）

- **不改动** `scripts/verify-E2E.sh` 本体。建议两种接入方式：
  1. **串联调用**（推荐验收时）：`bash scripts/verify-E2E.sh --skip-build && python -m test.obs_v4_tests.run_all`（verify-E2E 清库→起服务→seed→断言 L0==L1 & L2≤L0；随后跑 V4 测试）。
  2. **verify-only 衔接**：先手动起服务 + `python test/seed_all.py`，再 `python -m test.obs_v4_tests.run_all`（或 `run_all.py --seed` 让其自检并补 seed）。
- **断言不重复**：verify-E2E 已断言 L0==L1 & L2≤L0；V4 测试聚焦 T-A~T-N 新增契约，二者互补。
- 可在 verify-E2E 的 seed 步骤后、最终断言前插入 `python test/obs_v4_tests/run_all.py` 调用（脚本层集成），保持 verify-E2E 自身逻辑不变。
