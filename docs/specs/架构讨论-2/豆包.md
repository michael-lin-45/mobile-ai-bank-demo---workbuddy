# 整体前置说明
技术栈：Spring AI Alibaba 1.1.2 + SpringBoot3.4.3 + Agent Graph（智能体图编排）
目标能力：Trace追踪、会话回放、指标大屏
现有方案核心：**Advisor + AOP 拦截Graph执行链路，原始链路数据直接入库**

下面分三大问题完整解答，并给出落地架构、改造方案、代码思路、风险点。

## 一、问题1：基于现有Advisor架构扩展业务指标埋点方案
> 核心原则：**复用已有的Graph拦截切面，不新增大量埋点侵入业务代码；分层采集【AI原生指标】+【银行业务自定义指标】**

### 指标分层定义
#### 第一层：Agent/Graph/LLM 原生技术指标（框架侧指标）
从Advisor拦截上下文中直接提取，无需业务人工埋码
1. Graph链路指标
   - graph总执行耗时、单个节点执行耗时
   - Graph成功/失败次数、超时次数、异常类型分布
   - Graph跳转次数、分支选择频次（条件节点路由统计）
2. LLM调用指标
   - prompt tokens、completion tokens、总token
   - LLM调用耗时、重试次数、模型返回拒绝率（安全拦截）
   - 工具调用次数（Function Calling）、工具调用成功率
3. Memory记忆指标（你已实现长短记忆）
   - 记忆加载耗时、记忆条数、记忆召回命中/未命中

#### 第二层：业务自定义指标（手机银行场景，需要扩展上下文透传）
> 难点：点击率、咨询场景分布、转人工率、意图识别准确率这类指标**不在Graph原生返回数据里**，需要链路透传业务标签
示例指标：
- 会话点击率（用户发起对话次数）
- 业务场景分布：余额查询/转账咨询/信用卡/理财
- 意图识别准确率
- AI自动解决率 / 转人工会话占比
- 敏感咨询触发次数

### 基于Advisor实现埋点两种模式（推荐组合使用）
#### 方案A：Advisor统一拦截 + 上下文透传标签（优先推荐，低侵入）
1. **统一上下文载体**
扩展 `GraphAdvisor` 执行上下文，新建 `AiTraceContext`，统一承载全链路标签：
```java
public class AiTraceContext {
    private String sessionId;        //会话ID（会话回放主键）
    private String userId;           //用户ID
    private String sceneCode;        //业务场景：balance/transfer
    private String intent;           //识别意图
    private Boolean transferHuman;   //是否转人工
    private LocalDateTime startTime;
    // 链路原始指标、自定义业务标签
    private Map<String,Object> bizTags;
}
```
> 在Graph入口（对话接收处）初始化上下文，贯穿整个Graph执行链路。

2. **Advisor分层拦截时机**
Spring AI Graph Advisor提供前置/后置/异常回调，三个埋点时机：
```
beforeGraph() → 会话启动埋点（会话创建、场景标记）
afterGraph() → 正常结束：统计耗时、token、自动解决标记、会话结果
onError()     → 异常埋点：超时、LLM报错、graph执行异常
```

3. **指标分离存储思路（重点解决你“埋码复杂”痛点）**
- **日志/明细数据（Trace、会话回放）**：完整Graph节点明细、输入输出、对话原文 → 存入时序数据库/OLAP（ClickHouse），用于会话回放、链路排查
- **聚合指标（大屏指标）**：不使用明细实时聚合！Advisor拦截后，**指标数据发送至Metrics网关/消息队列，做预聚合**
  ✅ 禁止：每次查询大屏实时扫描全量会话明细（量大后查询爆炸）

#### 方案B：自定义指标注解 + AOP补充（用于零散业务埋点）
针对Graph外部的业务动作（例如【用户点击转人工按钮】不在Graph链路里）
新增注解 `@AiBizMetric(tag="transfer_human")`，复用现有AOP体系做埋点，作为Advisor能力补充。

### 数据输出选型（二选一，建议方案2）
1. 简单方案：Advisor内直接调用Micrometer(MeterRegistry)输出Prometheus指标
   - 优点：代码改动小；缺点：只能输出瞬时指标，无法携带会话维度标签（sessionId/userId），**不支持会话级多维度分析**
2. 生产推荐：Advisor组装完整指标事件 → 发送Kafka
   事件分为两类：
   - `AiTraceEvent`：明细事件（用于Trace、会话回放）
   - `AiMetricEvent`：聚合指标事件（用于指标大屏）

> 埋点伪代码示意
```java
@Override
public Flux<GraphResponse> beforeGraph(GraphAdvisorContext context) {
    AiTraceContext traceCtx = buildTraceContext(context);
    // 1. 会话启动指标事件
    sendMetricEvent(AiMetricEvent.builder()
            .metricName("ai.session.start")
            .tags(traceCtx.getBizTags())
            .timestamp(Instant.now())
            .build());
    return delegate.beforeGraph(context);
}

@Override
public Flux<GraphResponse> afterGraph(GraphAdvisorContext context, GraphResponse response) {
    AiTraceContext traceCtx = getTraceContext(context);
    // 采集LLM token、耗时、graph执行状态
    collectLLMMetrics(traceCtx, response);
    // 会话结束指标
    sendMetricEvent(buildSessionFinishMetric(traceCtx));
    // 写入明细Trace事件（会话回放数据源）
    sendTraceEvent(buildTraceRecord(traceCtx, response));
    return delegate.afterGraph(context, response);
}
```

### 解决「埋码复杂」核心手段
1. **标签中心化管理**：所有业务场景、意图编码统一枚举，避免硬编码；
2. **链路透传一次赋值，全程复用**：入口只赋值一次sceneCode、userId，Advisor全程读取，不用每个节点重复埋码；
3. **区分【自动采集指标】【人工标记指标】**
   - 自动：LLM耗时、token、graph节点耗时（无需开发埋码）
   - 人工：业务意图、转人工标记，仅在意图识别节点赋值一次

## 二、问题2：当前方案存在的缺陷 & 改造优化方案
> 当前架构总结：Advisor+AOP拦截Graph → 原始数据直接入库，明细库同时支撑Trace、会话回放、未来指标查询

### 现有方案主要问题
#### 1. 存储架构问题（最严重）
- 所有Graph原始明细直接入库（MySQL？），**读写耦合**
  会话回放需要完整对话文本、节点输入输出，数据量大；指标查询频繁扫描明细，随着手机银行会话上涨，库压力陡增；
- 明细与指标不分离：没有冷热分离，久远会话回放查询缓慢。

#### 2. 可观测标准缺失，没有对齐OpenTelemetry规范
Spring AI Alibaba官方原生支持OTel埋点，但你自建AOP+Advisor埋码：
- 无法复用标准可观测工具（Jaeger、Loki、Langfuse）
- Trace没有标准Span结构，无法和下游服务（用户中心、风控、消息服务）链路串联；
- 自定义Trace只能看Graph内部，无法完成**全服务分布式追踪**。

#### 3. 同步入库风险
Advisor拦截后**同步写数据库**：
Graph执行链路阻塞，如果数据库抖动、慢查询，直接拉长AI会话响应时间，影响手机银行前端体验（金融系统时延敏感）。

#### 4. 指标计算方式缺陷
现在计划：直接基于入库明细查询聚合指标。
问题：
- 高并发会话场景下，大屏实时聚合SQL极其消耗资源；
- 无法做分钟/小时预聚合；无法快速统计失败率、分场景指标。

#### 5. 边界覆盖不全
Advisor只能拦截**Graph内部执行流程**
以下业务事件无法捕获：
- 用户前端发起对话（点击AI助手入口=点击率指标）
- 用户主动结束会话
- Graph外部业务操作（转人工、风控拦截、前置鉴权）
这些业务指标无法通过Graph Advisor采集。

#### 6. 缺少采样、降噪策略
银行高峰期会话量大，如果全量采集全量存储，存储成本极高，没有设计采样策略（异常会话全采样，正常会话按比例采样）。

### 针对性改进方案
#### 改进1：数据流解耦，同步采集 → 异步消息队列
```
Graph执行 → Advisor组装TraceEvent/MetricEvent → 发送Kafka（非阻塞）
消费端双分支：
分支1：明细事件 → ClickHouse（存储Trace、会话回放明细）
分支2：指标事件 → Flink预聚合 → 写入时序库（InfluxDB/TimescaleDB/Prometheus）
```
✅ 核心收益：AI主链路不受存储、分析链路影响；支持峰值削峰。

#### 改进2：兼容OpenTelemetry，自建埋点与标准Span融合
不要完全抛弃现有Advisor，做兼容改造：
1. Advisor内部**同时创建OTel Span**，把Graph节点、LLM调用封装为标准Span；
2. 你自有TraceID 与 OTel TraceId做映射；
效果：
- 保留你现有会话回放能力（基于sessionId聚合）
- 同时打通全链路分布式追踪，可对接Jaeger、Langfuse

#### 改进3：分层存储设计（金融AI标准方案）
| 数据类型 | 存储引擎 | 用途 | 保存周期 |
|---|---|---|---|
| 全量Graph明细、对话原文 | ClickHouse | Trace详情、会话回放、问题排查 | 30~90天冷热分区 |
| 预聚合指标（分钟级） | TimescaleDB/Prometheus | 指标大屏、告警 | 90天 |
| 原始未聚合事件 | Kafka（消息留存） | 重放、数据修复 | 短期7天 |

禁止使用MySQL存储全量会话明细！

#### 改进4：完善指标采集边界
- Advisor负责【AI智能体内部指标】（Graph、LLM、工具调用）
- 对外提供统一埋点SDK `AiMetricClient`，在Controller、业务服务埋点捕获【前端/外部业务事件】（会话点击、转人工、鉴权）

#### 改进5：增加采样策略
- 异常会话（报错、超时、敏感咨询）：100%全采集
- 正常成功会话：支持动态比例采样（高峰期50%/30%），配置化开关

#### 改进6：数据脱敏（银行硬性要求！）
手机银行对话包含卡号、余额、身份证，Advisor拦截拿到prompt/response后，**入库之前强制脱敏**，否则合规风险巨大。你当前方案容易忽略！

## 三、问题3：业界 Spring AI / Spring AI Alibaba AI可观测主流实现方案
分成两条路线：**方案A 官方原生OTel埋点路线（轻量标准路线）**；**方案B 自建Advisor拦截+事件流方案（企业定制化路线，和你现状接近）**

### 路线1：Spring AI Alibaba 官方标准方案（社区主流）
底层基于 **OpenTelemetry + Micrometer**
Spring AI Alibaba 1.1.x 内置对ChatClient、ToolCall、Graph组件的自动Instrumentation
1. 自动创建Span：
   - LLM调用span、FunctionCall span、Graph节点span
2. 自动采集原生指标：token消耗、延迟、成功失败计数
3. 输出方式：
   - Traces → OTLP协议推送到OTel Collector
   - Metrics → Micrometer 上报Prometheus
4. 配套观测平台选型：
   - 通用分布式追踪：Jaeger、Grafana Tempo
   - **AI原生可观测平台：Langfuse、Arize AI、LangSmith**
> Langfuse可以直接接收OTLP数据，原生支持会话聚合、会话回放、LLM输入输出查看，非常贴合你的需求。

✅ 优点：标准化、零自建AOP、跟随框架版本升级、天然支持全链路追踪
❌ 不足：
- 框架原生Instrument只能捕获标准执行链路，**无法直接对接你自研Graph记忆模块**；
- 自定义业务标签（场景code、意图、转人工）需要手动注入Span Attribute；
- 会话回放需要自己做session维度聚合（框架不内置）；
- 金融场景需要深度定制脱敏、多租户、权限管控，开源平台很难直接落地。

### 路线2：企业自建增强方案（国内银行、证券AI智能体普遍采用，你当前方案属于此类）
架构范式：
`Advisor/AOP拦截Graph链路 → 组装AI事件 → MQ异步分发 → 流处理预聚合 → 多引擎存储 → 可视化大屏`
适用场景：自研Graph编排、自有记忆模块、强合规、深度业务定制（手机银行场景）

主流落地细节：
1. **埋点入口**
   - 优先复用Spring AI Graph Advisor（和你一致），不侵入业务Graph节点代码；
   - 补充Controller层全局拦截捕获会话起始业务标签
2. **数据传输标准**
   生产环境几乎不会同步入库，统一使用Kafka作为事件总线；事件采用Protobuf结构化定义。
3. **数据处理流水线**
   OTel Collector（可选） + Flink流处理
   职责：脱敏、过滤、采样、指标预聚合、异常识别
4. **可视化分层**
   - Grafana：指标大屏（接入Prometheus/Timescale）
   - 自研后台 / 增强Langfuse二次开发：Trace查询、会话回放

### 两种路线对比 & 给你的选型建议
| 维度 | 原生OTel官方方案 | 你当前自建Advisor增强方案（改造后） |
|---|---|---|
| 开发量 | 低，少量配置 | 中等，需要维护Advisor、事件、消费逻辑 |
| 业务定制能力 | 中等 | 极高（适配银行会话、脱敏、自定义业务指标） |
| 会话回放 | 需要自行开发聚合逻辑 | 已有基础，改造成本更低 |
| 分布式链路追踪 | 天然支持 | 需要兼容OTel做双向打通 |
| 合规脱敏、日志管控 | 需要额外开发 | 可内置在Advisor拦截阶段统一处理 |
| 升级兼容性 | 跟随Spring AI Alibaba升级 | 框架升级可能需要适配Advisor接口变更 |

👉 **最终建议：混合方案（最优折中）**
1. **保留现有Advisor架构**（不想推翻已开发的记忆拦截、会话回放能力）
2. 在Advisor内部**同时生成标准OTel Span**，打通标准可观测体系；
3. 事件异步发送Kafka，移除同步入库；
4. Trace明细入ClickHouse支撑会话回放；指标通过流预聚合提供大屏；
5. 未来逐步将通用指标迁移至Spring AI原生Instrument，Advisor仅承载业务定制逻辑。

## 四、落地实施优先级建议（可以直接用于项目排期）
1. P0：改造数据流，同步入库 → Kafka异步事件，新增数据脱敏逻辑（金融最高优先级）
2. P1：扩展Advisor埋点模型，完善AiTraceContext上下文标签体系，区分【技术指标/业务指标】
3. P2：搭建消费链路：ClickHouse明细存储 + Flink预聚合指标
4. P3：适配OpenTelemetry，打通标准Trace，支持跨服务追踪
5. P4：指标大屏开发、会话回放UI优化、采样策略配置化
6. P5：逐步落地告警规则（LLM超时激增、Graph异常率上涨、会话失败告警）

## 五、补充风险提示（银行项目重点）
1. **用户对话文本属于敏感数据**：所有Trace存储必须脱敏，控制访问权限；
2. Spring AI Alibaba Graph Advisor接口后续版本可能调整，建议封装一层门面，隔离框架API；
3. 不要在Advisor中执行业务逻辑，只做拦截、采集、转发，避免影响智能体主流程；
4 Token统计注意区分输入Token、输出Token，银行算力成本核算需要该指标做分摊。
