# V23 DEMO 设计 vs 前端实现 — 设计优劣评估报告

> 评估人：许清楚（产品经理）
> 评估日期：2026-07-24
> 评估对象：银行 AI 可观测平台仪表盘 — DEMO v23 设计稿 vs 前端 React 实现
> 数据来源：`可观测V23-前台与DEMO差距报告-2026-07-24.md` + 前端源码复核

---

## 1. 评估框架说明

本报告从三个维度对每个差距进行评分，每维度用 **★/☆** 标记倾向（★ = 该维度下该方案更优），必要时给出折中建议。

### 三维度定义

| 维度 | 关注点 | 核心问题 |
|------|--------|----------|
| **UX 视角** | 信息效率、操作路径长短、认知负荷 | 用户一瞥能看到多少有用信息？需要几步操作才能完成核心任务？ |
| **运营视角** | 日常使用场景下的行动驱动力、问题定位效率 | 这个设计能否让运营人员在 30 秒内判断「有没有问题、问题在哪、该做什么」？ |
| **工程视角** | 数据可得性、维护复杂度、是否与已有区块重复 | 实现成本多高？会引入多少维护负担？是否存在信息冗余？ |

### 评分符号

- `★` ：该维度该方案明显更优
- `☆` ：该维度该方案略优
- `—` ：该维度两方案相当或无法区分

## 2. 逐项分析

---

### A. AI 洞察 TAB 顺序（P1-1）

#### 两方案对比

| | 前端顺序 | DEMO 顺序 |
|---|---|---|
| 1 | 智能诊断 | 智能诊断 |
| 2 | 准确率分析 | 准确率分析 |
| 3 | Agent 性能 | Agent 性能 |
| 4 | **Token 成本** | **业务转化漏斗** ← 不同 |
| 5 | **外部调用** | **Token 成本** ← 不同 |
| 6 | **业务转化漏斗** | **外部调用** ← 不同 |
| 7 | 用户满意度 | 用户满意度 |

#### 优劣分析

**前端方案的语义分组逻辑**（附带 persona 副标题）：

```
Group 1「AI 技术质量」  → 诊断(诊断看) → 准确率(算法看) → 性能(开发看)
Group 2「成本与基础设施」→ Token成本(成本看) → 外部调用(调用链看)
Group 3「业务成果」      → 转化漏斗(产品看) → 满意度(体验看)
```

这是一个非常清晰的 **技术 → 成本 → 业务** 递进逻辑。运营人员从左到右扫描 TAB 时，心智模型是：「AI 跑得对不对 → 花了多少钱 → 带来了什么价值」。三个组内各自语义内聚，组间边界清晰。

**DEMO 方案的顺序**：

```
诊断 → 准确率 → 性能 → 漏斗 → Token → 外部调用 → 满意度
```

问题在于：第 4 位「漏斗」是纯业务指标，第 5-6 位又回到技术/成本，第 7 位又回到业务（满意度）。这造成了 **业务→技术→业务** 的 zigzag，认知上不流畅。用户扫 TAB 时会产生「怎么又回到成本了」的困惑。

从**使用频率**角度：在 AI 运营的日常工作中，诊断 TAB 是高频入口（出了问题首先看），准确率和性能是中频（定期巡检），Token 成本和外部调用是低频（月底/问题排查时看），漏斗和满意度是业务侧关心的中频指标。前端的顺序（诊断→准确率→性能→成本→调用→漏斗→满意度）恰好是从高频到低频递减，符合费茨定律中「常用功能靠左」的原则。

DEMO 把漏斗提前到第 4 位的意图可能是强调「业务转化是核心」，但这在运营场景下不太成立——运营人员进入 AI 洞察页面，首要任务是判断「AI 系统有没有出问题」，而不是「今天转化了多少」。转化漏斗更适合在独立业务报表中查看，或在总览大屏用关键数字体现。

#### 打分

| 维度 | 前端 | DEMO | 说明 |
|------|:----:|:----:|------|
| UX 视角 | ★ | | 语义分组清晰，技术→成本→业务递进自然，无 zigzag |
| 运营视角 | ★ | | 高频→低频递减，诊断入口靠左符合操作习惯 |
| 工程视角 | ★ | | 已实现，且有副标题辅助定位目标用户；改回 DEMO 需重排数组但无技术风险 |

#### 倾向性结论

**推荐前端方案（保持现状）**。

DEMO 的漏斗→Token→外部调用顺序缺乏语义分组逻辑（业务指标插入技术指标中间），不如前端的「技术→成本→业务」三组递进清晰。DEMO 此处设计不佳。

### B. 总览大屏「诊断摘要」4 卡（P1-2）

#### 两方案对比

| | 前端方案 | DEMO 方案 |
|---|---|---|
| 卡片1 | 意图识别综合正确率 (KPI 数值) | 性能瓶颈 (2起, 🔴红) |
| 卡片2 | 意图改写正确率 L1 (KPI 数值) | 准确率风险 (3起, 🟡黄) |
| 卡片3 | 重路由比率 (KPI 数值) | 转化流失 (1起, 🟣紫) |
| 卡片4 | 业务完成率 (KPI 数值) | 满意度 (4.1分, 🟢绿) |
| 视觉风格 | 白底 + 左侧彩边 + 等宽数字 | 彩色背景 + 彩色边框 + 彩色大字 |
| 点击行为 | 全部跳诊断 TAB | 各卡跳对应诊断 TAB |
| 数据来源 | RealtimeMetricsVO | insights 聚合（风险计数） |

#### 优劣分析

这是 5 个差距中**最重要**的一个，因为它直接影响运营人员打开 dashboard 的第一眼体验。

**前端方案的核心问题：与 Zone C/D 重复**

前端的 4 张 KPI 卡（综合正确率/改写正确率/重路由/完成率）与下方紧邻的 Zone C（语义质量）和 Zone D（业务效果）**完全重复**：

- Zone C 第 1 卡 = 综合正确率（= 前端卡 1）
- Zone C 第 2 卡 = 改写正确率（= 前端卡 2）
- Zone C 第 3 卡 = 重路由比率（= 前端卡 3）
- Zone D 第 1 卡 = 业务完成率（= 前端卡 4）

这不是「红绿灯 + 详情」的两层设计——前端 4 卡和 Zone C/D 卡展示的是**同样的数据、同样的格式（KPI 数值）**，只是位置不同。用户看完顶部 4 卡，往下翻一屏又看到一模一样的数字，这是纯粹的信息冗余。在 dashboard 设计原则中，每一寸屏幕空间都应该承载独特的信息价值。

**DEMO 方案的优势：问题导向的行动信号**

DEMO 的 4 张风险卡是经典的「红绿灯仪表盘」模式，在运维/监控领域被广泛验证有效（如 Datadog、Grafana、PagerDuty 的告警面板）：

1. **信息效率极高**：运营人员打开页面，0.5 秒内扫过红/黄/紫/绿四色，立刻知道「性能有 2 个问题、准确率有 3 个风险」。不需要读数字、不需要判断阈值。
2. **强行动驱动**：红色 = 立即处理，黄色 = 关注，紫色 = 排查，绿色 = 放心。每张卡片直接下钻到对应诊断 TAB，操作路径从「扫 KPI → 判断是否异常 → 找对应 TAB」缩短为「看颜色 → 点击」。
3. **与 Zone C/D 互补而非重复**：Zone C/D 展示的是实时 KPI 数值（what），诊断摘要展示的是风险计数（so what）。两者是不同层次的信息，互相补充。

**关于「重复」是否可以是两层设计**：两层设计的合理形态是「摘要 + 详情」，摘要必须比详情更抽象、更高维度。前端的 4 卡和 Zone C/D 是同维度的（都是百分比 KPI 数值），不是摘要和详情的关系。DEMO 的「风险计数」和 Zone C/D 的「KPI 数值」才是不同维度，构成真正的两层结构。

#### 打分

| 维度 | 前端 | DEMO | 说明 |
|------|:----:|:----:|------|
| UX 视角 | | ★ | DEMO 用颜色编码风险，一瞥即可判断系统状态；前端需要逐一阅读 4 个数字并与心理阈值比较 |
| 运营视角 | | ★ | DEMO 驱动行动（红=立即处理），前端只呈现数据不给出判断 |
| 工程视角 | ☆ | ★ | 前端实现简单但信息冗余；DEMO 需要新增风险计数聚合接口，但换来的是独特信息价值，ROI 合理 |

#### 倾向性结论

**强烈推荐 DEMO 方案**。前端的 KPI 卡片与 Zone C/D 完全重复，是设计上的硬伤。DEMO 的「风险计数 + 彩色编码 + 分卡下钻」是运维仪表盘的成熟模式，应采纳。**前端此处设计不佳，需修改。**

唯一需要关注的工程风险：风险计数的定义需要明确（什么算「性能瓶颈」？阈值是多少？），避免误报过多导致「狼来了」效应。建议初期阈值宽松，逐步收紧。

### C. 智能诊断 TAB 慢会话根因表（P1-3）

#### 两方案对比

| | 前端方案 | DEMO 方案 |
|---|---|---|
| 结构 | 逐条会话明细列表 | 按根因类别聚合 |
| 列 | 会话ID / 时长 / 轮次 / 意图流 / 操作 | 根因类别 / 会话数 / 占比 / 平均耗时 / 主要Agent / 建议 |
| 交互 | 可展开单条会话的根因候选列表 | 条件触发（P90>3s 时展示，否则绿色状态） |
| 典型问题 | 50 条慢会话时，用户需逐个展开才能知道根因分布 | 直接看到「40% 是 LLM 推理慢，30% 是外部 API 超时」 |

#### 优劣分析

这个差距的本质是：**诊断场景下，你更需要「地图」还是「街景」？**

**前端方案（街景）**：给你每条慢会话的详情，像 Google Street View 一样能看到每个具体案例。适合「这个用户投诉了，我要查他的会话」的场景。但这不是诊断的主路径——诊断的主路径是「系统现在有什么问题？最需要修什么？」

**DEMO 方案（地图）**：给你按根因类别的聚合视图，像地图一样先看到全景。运营人员的典型工作流是：

1. 打开诊断 TAB → 看到慢会话根因聚合表
2. 「大模型推理超时」占 45%，是最主要根因 → 点击展开该类别下的具体会话
3. 针对「大模型推理超时」这个根因，去性能 TAB 或通知开发团队

DEMO 方案完美支持这个工作流。前端方案把这个工作流的第 1 步跳过了，直接让用户面对几十条会话列表，要求用户自己「手动聚合」出根因分布——这对运营人员来说认知负荷太高。

**工程视角的额外考虑**：
- 前端方案在慢会话数量多时（如 200+）会面临性能和可读性问题
- DEMO 的聚合表天然可扩展，根因类别数量通常有限（5-15 类），不受慢会话总量影响
- DEMO 的条件触发（P90>3s）避免了「没有慢会话时还展示一个空表」的尴尬

**最优方案建议**：DEMO 的聚合表作为默认视图，但增加可点击的根因类别行，展开后显示该类别下的具体会话列表（可复用前端已有的会话详情结构）。这样「地图 + 街景」兼得。不过这是增强建议，当前 DEMO 聚合表本身已经优于前端逐条列表。

#### 打分

| 维度 | 前端 | DEMO | 说明 |
|------|:----:|:----:|------|
| UX 视角 | | ★ | DEMO 一眼看到根因分布；前端需要手动扫描和心智聚合 |
| 运营视角 | | ★ | DEMO 直接回答「什么根因占比最高」这个运营核心问题 |
| 工程视角 | | ★ | DEMO 聚合表随数据量增长性能稳定；前端逐条列表在大数据量下会退化 |

#### 倾向性结论

**强烈推荐 DEMO 方案（聚合表）**。逐条会话明细更适合放在「会话回放/链路追踪」页面，而非诊断首页。诊断的核心价值是「聚合 → 发现模式 → 定位根因」，DEMO 的聚合表更贴合这个目的。**前端此处设计不佳，需修改。**

### D. 智能诊断 TAB 不满意共性表（P1-4）

#### 两方案对比

| | 前端方案 | DEMO 方案 |
|---|---|---|
| 列1 | 维度 | 共性维度 |
| 列2 | 会话数 | 分类 |
| 列3 | 共性模式（文字描述） | 不满意数 |
| 列4 | 示例会话 | 不满意率 |
| 列5 | — | **全局均值** |
| 列6 | — | **偏差** |

#### 优劣分析

**信息密度对比**：

前端 4 列中，「共性模式」是定性文字（如「用户多次追问后仍未得到满意答复」），「示例会话」是 ID 列表。这两个字段对**理解问题本质**有帮助，但对**量化问题严重程度**帮助有限。

DEMO 6 列中，**「全局均值」和「偏差」是关键差异化字段**。举例：

| 共性维度 | 不满意数 | 不满意率 | 全局均值 | 偏差 |
|----------|---------|---------|---------|------|
| 响应速度慢 | 120 | 28% | 12% | **+16%** |
| 理解错误 | 45 | 10% | 12% | -2% |

有了「全局均值/偏差」，运营人员立刻知道「响应速度慢」的不满意率是全局均值的 2.3 倍，这是一个显著的异常信号。而「理解错误」虽然也有 45 个不满意，但它和全局均值差不多，说明这是系统级的普遍问题而非该维度的特有问题。

**没有「全局均值/偏差」会发生什么？**

运营人员看到「响应速度慢：120 个不满意」，可能会觉得这是最大的问题。但实际上，如果「响应速度慢」这个维度的总请求量也很大（分母大），不满意率可能并没那么高。而另一个维度「金额识别错误」可能只有 30 个不满意但占该维度总量的 60%，远比 28% 严重。没有基准值，就无法判断什么是「异常」。

**DEMO 的「分类」列的价值**：将不满意维度归类（如「技术类」「业务类」「体验类」），有助于识别问题是集中在哪个领域，辅助资源分配决策。

**前端「共性模式」和「示例会话」的价值**：这两个字段在 DEMO 中缺失，但它们确实有价值——「共性模式」提供上下文，「示例会话」支持抽查验证。建议 DEMO 方案增加这两个字段作为可选列或详情展开。

#### 打分

| 维度 | 前端 | DEMO | 说明 |
|------|:----:|:----:|------|
| UX 视角 | | ★ | DEMO 的「偏差」列让异常一目了然；前端无参照系 |
| 运营视角 | | ★ | DEMO 直接回答「哪些维度显著偏离正常水平」，可操作性强 |
| 工程视角 | | ★ | DEMO 需要额外计算全局均值，但这是简单聚合，成本低 |

#### 倾向性结论

**推荐 DEMO 方案**。「全局均值/偏差」是不满意分析的核心——没有参照系的数字没有决策价值。前端的「共性模式」文字描述有补充价值，建议 DEMO 方案额外增加或作为展开详情保留。**前端此处设计需修改，但可保留「共性模式」字段作为增强。**

### E. 准确率 TAB 顶部 KPI 汇总卡（P1-5）

#### 两方案对比

| | 前端方案 | DEMO 方案 |
|---|---|---|
| 顶部区块 | 4 张 KPI 汇总卡（整体/改写/混淆率/样本量）| 无，直接从趋势图开始 |
| 卡片样式 | InsightKpiCard 组件，带颜色编码 | — |
| 趋势图副标题 | 取 overallStats[0] 显示 | 副标题「L0 98.2%·L1 94.2%·整体 ↑1.8%」 |

#### 优劣分析

这个问题的核心是：**用户进入准确率 TAB 时，已经知道了什么？还需要知道什么？**

**用户进入准确率 TAB 的路径分析**：

1. **从总览大屏进入**：总览的 Zone C 已经显示了综合正确率、改写正确率。用户点击进入准确率 TAB 时，这些数字刚看过，4 张 KPI 卡是冗余的。
2. **从诊断 TAB 的「去准确率 TAB」链接进入**：用户带着一个具体问题来的（如「准确率风险 3 起」），他们需要的是趋势详情和根因分析，而非一个总览数字。
3. **从外部链接直达**：如果用户通过书签或告警链接直接进入准确率 TAB，没有看过总览大屏。此时顶部 KPI 卡提供了一次快速定位——但趋势图的副标题（如 DEMO 的「L0 98.2%·L1 94.2%·整体 ↑1.8%」）已经提供了同样的信息。

**4 张 KPI 卡是否「有用速览」还是「信息冗余」？**

在准确率 TAB 的上下文里，这 4 张卡属于**轻度冗余**——不算严重的设计错误，但增加了页面长度和视觉噪音，却没有提供足够独特的信息价值。用户在准确率 TAB 的核心任务是：看趋势是否下滑、看改写准确率详情、看混淆矩阵找问题类别。KPI 汇总对于这些任务没有直接帮助。

**但也不应一刀切移除**。考虑一种折中方案：

**推荐折中：单行摘要条替代 4 卡**

保留准确率 TAB 顶部的 quick-glance 功能，但不使用占空间大的 4 张 KPI 卡片，而是改为一行紧凑的摘要条：

```
整体意图准确率 94.2% ↑1.8%  |  改写准确率 L1 91.5%  |  混淆率 3.2%  |  样本量 12.8k
```

这一行占用的垂直空间约为 4 卡的 1/4，但保留了关键数字的可扫描性。这类似 DEMO 趋势图副标题的思路，但扩展到涵盖 4 个核心指标。

前端已有的 `normalizeOverallStats` 容错逻辑（兼容字符串和数组两种后端返回）是好的工程实践，可以在折中方案中继续使用。

#### 打分

| 维度 | 前端 | DEMO | 说明 |
|------|:----:|:----:|------|
| UX 视角 | | ★ | DEMO 更简洁，减少垂直滚动；4 卡在 TAB 内页略显冗余 |
| 运营视角 | ☆ | ★ | DEMO 让用户更快到达核心内容（趋势图）；但 4 卡对直达场景有微弱价值 |
| 工程视角 | ★ | ☆ | 前端已实现且有容错逻辑，移除成本低；DEMO 更简单但丢失了 quick-glance |

#### 倾向性结论

**推荐折中方案：移除 4 张 KPI 卡片，替换为单行摘要条**。

纯 DEMO 方案（完全无顶部汇总）对于从外部直达准确率 TAB 的场景缺少 quick-glance。纯前端方案（4 张 KPI 卡）对从总览进入的场景是冗余。折中方案平衡了两者。**DEMO 和前端在此处各有不足，折中最优。**

## 4. 对 DEMO 设计的反馈

虽然 5 个差距中有 4 个推荐了 DEMO 方案，但 DEMO 本身并非完美。以下是指出其设计不当之处：

### 4.1 TAB 顺序设计不合理（差距 A）

DEMO 的 `诊断→准确率→性能→漏斗→Token→外部调用→满意度` 顺序缺乏明确的排序逻辑。第 4 位插入的「漏斗」是业务指标，紧随其后的「Token/外部调用」又是技术指标，最后「满意度」又跳回业务。这给用户造成的认知路径是技术→业务→技术→业务，像 ping-pong。

**建议**：DEMO 应参考前端的「技术→成本→业务」三组递进逻辑调整 TAB 顺序。如果 DEMO 设计者认为「漏斗」作为核心业务指标需要更靠前，可以保持在前端方案的 Group 3 首位（即第 6 位），但在 Group 1 和 Group 2 之后——这符合「先确认系统正常，再看业务价值」的运营思维。

### 4.2 不满意共性表缺少定性字段（差距 D）

DEMO 的 6 列表格（共性维度/分类/不满意数/不满意率/全局均值/偏差）定量分析很强，但缺少前端已有的「共性模式」（文字描述）和「示例会话」。在运营实际中，运营主管经常需要把表截图发给相关团队——一段文字描述（如「用户多次追问后转人工」）比数字更有说服力。

**建议**：在 DEMO 表中增加「共性模式」列（可放在「分类」之后），或将「示例会话」作为行展开的详情。这不仅提高了可操作性，也提升了跨团队沟通效率。

### 4.3 准确率 TAB 信息架构可优化（差距 E）

DEMO 准确率 TAB 直接从趋势图开始，虽然简洁，但对于通过外部链接（如告警邮件）直达该页面的用户来说，缺乏快速定位当前状态的锚点。单行摘要条是比「无任何汇总」和「4 张 KPI 卡」更好��折中。

## 5. 总结

| 指标 | 数值 |
|------|------|
| 总差距评估数 | 5 |
| 推荐 DEMO 方案 | 3（B/C/D） |
| 推荐前端方案 | 1（A） |
| 推荐折中方案 | 1（E） |
| DEMO 设计被指出问题 | 3 处（§4.1 / §4.2 / §4.3） |

**核心发现**：

- **差距 B（诊断摘要 4 卡）** 是最关键的差异，直接影响 dashboard 首页的信息架构。前端当前方案与 Zone C/D 的重复是明确的硬伤，应优先修复。
- **差距 C/D（诊断 TAB 两张表）** 体现了「明细导向」和「聚合导向」两种设计哲学的差异。在诊断/监控场景下，聚合优于明细——先看到全景，再深入细节。
- **差距 A（TAB 顺序）** 是 DEMO 少数不如前端的地方。前端的三组递进逻辑更合理。
- **差距 E（准确率 KPI 卡）** 属于轻度问题，折中方案可兼顾双方优点。

**建议修改优先级**：B → C → D → E → A（A 不改前端，其他按此顺序修改前端代码）。
