## start-all.ps1 支持 Ctrl+C 安全清理
- 问题：原脚本用 `Start-Process` 后台拉起 Redis/Collector/Backend/Core/Frontend，但 Ctrl+C 只中断 PowerShell 主进程，子进程(otelcol/java/node)全变孤儿。
- 修复：整段启动流程外套 `try { ... } finally { if ($global:CtrlC) { global:Stop-AllServices } }`；注册 `Register-ObjectEvent -InputObject ([Console]) -EventName CancelKeyPress` 置 `$global:CtrlC=$true` 并直接调清理（安全网）。
- `Stop-AllAndExit` 重构为调用 `global:Stop-AllServices`（幂等 guard `$global:CleanedUp`，按 otelcol 进程名 + 各端口杀），错误路径保持 pause+exit 1；端口清单 8888→8887 对齐 `$COLLECTOR_PROM`。
- 关键：`Stop-PortOccupier`/`Stop-AllServices` 改 `function global:`，事件处理器子作用域才能调用。正常退出(按任意键)不清理、服务继续运行；仅 Ctrl+C/失败才清理。

## 沉淀可复用脚本 scripts/verify-E2E.sh
- 把上述 E2E 验证全流程固化成 Bash 脚本（Git Bash 环境），支持 `--skip-build / --verify-only / --stop-after / --turns N / --help`。
- 断言改为鲁棒核心不变量：**L0==L1（每请求一个 L0，正是原 bug 的判据：修复前 L0<L1）** + **L2≤L0** + **distinctOpNames 含 L0:DomainRouter**。不再用脆弱的 `==36`（seed 偶发 HTTP 错误会使 L0 略小于 36，但 L0==L1 仍成立）。
- 落地时踩坑并修复（均已验证）：
  1. **MSYS 路径转换**：Git Bash 把 `$PROJECT_ROOT` 解析成 `/d/...`，直接传给 Windows 原生 `java -jar`/`otelcol.exe`/`python seed` 会找不到文件（且项目路径含空格）。所有传给原生程序的路径统一用 `cygpath -w` 转成 `D:\...` 形式（CORE_JAR_W/BACKEND_JAR_W/AGENT_JAR_W/COLLECTOR_DIR_W/SEED_SCRIPT_W）。
  2. **backend CWD**：backend 的 H2 是相对 `./data/observability`，落点取决于 CWD。脚本须 `cd observability/backend/` 启动（符合 MEMORY SOP），否则 H2 落到项目根 `data/` 而清理 rm 只删 `backend/data/` → 数据跨运行累积。修复：启动 backend 用子 shell `( cd "$BACKEND_DIR" && exec nohup java ... ) &`，清理时同时删两处 H2。
  3. **`$!` 未绑定**：子 shell 内 `&` 会使父 shell 的 `$!` unbound（`set -u` 报错）。改为外层 `&` + 子 shell 内 `exec`，使 `$!` 在父 shell 可见。
- 最终验证：干净态运行 `./scripts/verify-E2E.sh --skip-build` → 库从 0 起、seed 后 l0=34=l1=34、l2=10≤34、L0:DomainRouter 存在 → ✅ 通过（34 因 2 轮 seed HTTP 错误，L0==L1 证明修复生效）。
- 使用：日常改动后跑 `bash scripts/verify-E2E.sh --skip-build` 一键回归可观测性修复。
