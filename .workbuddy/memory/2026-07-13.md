### 🔴 根因：traceId 跨请求泄漏（清库重播新暴露，最早 98968ms 延迟异常的真因）
- **现象**：36 请求塌缩成 ~10 个 traceId，同一 session 多请求挤进一个 trace，duration 高达 99s~155s、intent 串标、status=ERROR、ttft=0。
- **根因**：`src/main/java/com/mobileagent/app/observability/ObsChatModel.java` 的 `startBusinessSpan()` 里 `Context.current().with(baggage).makeCurrent()` 返回的 Scope **从未 close()** → 破坏线程 OTel 上下文栈平衡 → 线程池复用时下一请求的 server span 挂到残留上下文 → traceId 泄漏。
- **修复**：
  1. `ResolvedCtx` 新增 `baggage` 字段。
  2. `startBusinessSpan()` 不再自行 makeCurrent，改为把 baggage 存入 `rc.baggage`。
  3. 新增 `openScope(span, rc)` 辅助方法：把 span + baggage 合并进【同一个】Scope。
  4. `call()`(line 116) / `stream()`(line 188) 的 `span.makeCurrent()` 改为 `openScope(span, rc)`——该 scope 由 finally / doOnComplete / doOnError 统一 close，上下文栈严格平衡。
- **教训**：任何 `makeCurrent()` 返回的 Scope 必须配对 close()，否则线程复用必然泄漏 traceId。此前改直方图桶估算只是治标（掩盖 98968ms 数值），泄漏才是本源。

### 🔴 根因二：stream() 流式路径 Scope 跨线程 close 无效（继上，第二次清库重播暴露）
- **现象**：修完 call() 后重播仍 36 请求→35 distinct traceId；np4 连续两轮流式 WEALTH_CONSULT 合并成 1 条（仅 2 trace），np1 流式轮列表 duration=61753ms（明细仅 3101ms，虚高）。
- **根因**：`ObsChatModel.stream()` 在**装配线程**用 `openScope(span, rc)` 打开 Scope，但 `Flux` 的 `doOnComplete`/`doOnError` 运行在**与装配线程不同的 reactor 调度线程**上——线程本地 Scope 在别的线程 close() 无效 → 装配线程 OTel 上下文栈永不恢复 → 下一流式请求继承残留上下文 → 合并/虚高。
- **修复思路**：业务 span 已在装配线程用「当前干净上下文」创建，自带正确 parent 与独立 traceId；流式路径**根本不需要**在装配线程 makeCurrent()。改为：
  1. 删除 stream() 装配线程的 `Scope scope = openScope(span, rc);`（加注释说明根因）。
  2. `doOnComplete`/`doOnError` 移除 `scope.close()`，仅保留 `span.end()`（后续操作仅通过 span 引用 `setSpanAttribute`/`span.end()`，不依赖 ThreadLocal 当前上下文）。
  3. 新增 `doOnCancel` 兜底：SSE 客户端提前断开时 `setSpanAttribute(span,"cancelled","true")+span.end()`，避免 span 悬挂。
  4. `call()`（非流式）仍保留 `openScope`（同线程 try-finally close，已验证干净）；`openScope` 辅助方法保留。
- **教训**：Reactor 的 doOn* 回调不在装配线程执行，任何线程本地资源（OTel Scope/ThreadLocal）都不能"装配线程开、回调线程关"。流式场景应直接持 span 引用操作，绕开 ThreadLocal 当前上下文。

## 方案A修复：DomainRouter确定性路由补全L0 span（2026-07-13 续，闭环上节Bug#1）

### 背景与根因
- 上节实测 L0(23)<L1(36)、L2(12)≤L0(23)。计数逻辑无 bug（`getAgentCallCountsFromSpans` 按 `COUNT(DISTINCT trace_id)` 去重）。根因在 Core `DomainRouter.route()` 双分支：①确定性路由 `routeDeterministic()` 关键词命中即 `return`（不调 LLM、不创建 span）；②仅 LLM 兜底路由经 `AgentSpanContext.setWithHeldSpan("L0",...)`/`ObsChatModel` 创建 L0 span → 确定性请求无 L0。

### 修复（方案A，用户选定）
- 文件 `src/main/java/com/mobileagent/app/router/domain/DomainRouter.java`：确定性分支 `return deterministic` 前，直接经 `GlobalOpenTelemetry.getTracer("obs-chat-model")` 创建 `L0:DomainRouter` span 并立即 `end()`。
- 设计要点：
  - 不走 `setWithHeldSpan`/`commitIntent`：因该 return 在 try-finally（仅覆盖 LLM 分支）之外，用 held 模式会因 clear 不执行而泄漏 liveSpan。
  - 直接经 Tracer 创建 + 立即 end；parent 自动取当前 server span，与 LLM 路径 OTel 树结构一致；后端 `buildSpanTree` 按真实 parentSpanId 建树、`determineLayer` 按 opName 前缀缩进 → 确定性 L0(`L0:DomainRouter`) 与 LLM L0 前端渲染一致。
  - **绝不 makeCurrent**：沿用 traceId 跨请求泄漏教训，避免线程 OTel 上下文栈残留。span 仅覆盖路由决策、立即 end，无悬挂风险。
  - 新增 `routing.mode=deterministic` 属性区分两种 L0 来源（LLM 路径缺省 llm）。
- 编译验证：`./mvnw.cmd compile -DskipTests -o` EXIT=0。
