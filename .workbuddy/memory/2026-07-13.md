## 修复 trace 列表 sessionId 携带 `\n`（以及指标 P95/P99 异常）
用户反馈：(1) 首 Token 时延 P95/P99、P95 系统时延最大值到 98968ms，明显异常；(2) 手工下发的 3 次转账 trace 在 session 视图看不到；(3)（本轮）trace 携带的 `\n` 要删掉。

### 指标异常（Task #5，已完成代码）
- 根因：`OtlpParserService` 把 histogram 的 `sum/count` 均值当单个样本写入 ZSET，早期一次慢请求 avg 飙到 98968ms 污染 P99。
- 修复：`OtlpParserService` 改为从 `bucketCounts`+`explicitBounds` 估算 P50/P95/P99（新增 `histogramPercentile` 辅助方法）；`RedisMetricsService` 新增 `setLatencyPercentiles`/`setTTFTPercentiles` 写入 Hash，并让 `getTTFTStats`/`getLatencyStats` 优先读 Hash 的准确分位。

### session 列表筛选只对当前页生效（Task #6，已完成代码）
- 根因：`SessionService.listSessions` 只在 `result.getContent()`（当前页）上做 in-memory 过滤，搜 `test3` 返回 0。
- 修复：`SessionRepository` 增加 `findAllByTimeRange`/`findAllByTimeRangeAndStatus`；`listSessions` 改为全量拉取→trim+过滤→手动分页；`upsertSession` 对 sessionId 做 trim。

### trace 携带 `\n`（本轮）
- 根因：`BankController.chat/getState/clearSession` 入口未 trim，带换行 `\n` 的 sessionId 原样传入 `AgentSpanContext` → `ObsChatModel` 写进 span 的 `session_id` 属性（第 455 行），而 `SessionBridge` 第 57 行有 trim 所以 session 表是干净的。trace 列表/详情从 `parseAttributes` 透传 `test3\n`，且用带 `\n` 的 sessionId 查 session 表匹配不上。
- 修复（三处）：
  1. Core `BankController` 三个入口 `sessionId = sessionId.trim()` —— 杜绝新 trace 再带 `\n`。
  2. Core `ObsChatModel.startBusinessSpan` 写 `session_id`/`user_id` 属性与 Baggage 前强制 `.trim()` —— 防御性，存储层永不再带 `\n`。
  3. 后端 `TraceQueryService.parseAttributes` 读取时对 `session_id/sessionId/user_id/userId` 做 trim —— 已存储的 3 条老 trace 显示即变干净、`test3\n` 不再出现、trace→session 关联恢复。
- 说明：`extractSessionIdFromUrl` 早就有 `.trim()`，所以 `\n` 不是来自 url.query，是来自业务 span 的 `session_id` 属性。
- 未做 H2 物理 DELETE（风险：JSON 内 `\n` 可能是转义符，REPLACE 会误伤 ai.io.response 等含换行的字段）；读取层 trim 已彻底解决可见问题与关联问题。
