## start-all.ps1 端口占用检查修复
- **问题**：4 处 `Stop-PortOccupier` 返回值被 `| Out-Null` 丢弃，端口杀不掉时（权限不够等）脚本仍继续启动新进程，造成重复占用

## H2 数据库膨胀 + 慢启动修复

### 根因
- H2 数据库文件 `observability.mv.db` 膨胀到 **508 MB**
- metrics_agg 表有 83 万条 6月30日之前的旧记录
- Backend 启动时打开+解析 508MB MVStore 超过 120 秒，脚本 Wait-Url 超时

### 清理结果
- 删除 6月30日之前数据：spans(6,396) + logs(2,717) + sessions(18) + session_turns(118) + metrics_agg(832,468) + agent_performance(5) + token_cost(4) + tool_calls(4) = **841,730 行**
- SHUTDOWN COMPACT 后：**508 MB → 80 MB**（压缩比 6.3x）

### 治本方案
- 新建 `DataCleanupService.java`：`@PostConstruct` 启动时清理 + `@Scheduled(cron="0 0 3 * * ?")` 每日凌晨 3 点自动清理
- 保留策略：7 天（RETENTION_DAYS = 7）
- `ObservabilityBackendApplication` 添加 `@EnableScheduling`
- start-all.ps1 Backend 超时：40×3s → 60×5s (120s → 300s)

## SessionBridge 超时问题诊断与修复

### 根因
- Core SessionBridge POST /api/v1/sessions → Backend 9090 超时
- Backend 端口 9090 监听但 **71 个 CLOSE_WAIT 连接泄漏**耗尽 Tomcat 线程池
- 泄漏源：OTel Collector (PID 1600) 每次推送 OTLP metrics/traces 后，后端 Tomcat worker thread 未正确 close() socket
- 后果：新 HTTP 连接无法分配到 worker thread → connect/request timeout

### 修复措施
- 杀死旧后端进程 (PID 30556)，重启显式指定 `-Dserver.port=9090`
- application.yml 增加 Tomcat 连接配置：
  - connection-timeout: 10s（默认 20s）
  - keep-alive-timeout: 15s（强制回收僵尸连接）
  - max-connections: 200, accept-count: 50（限流防堆积）
  - shutdown: graceful（防止重启残留）

### 验证
- POST /api/v1/sessions → HTTP 200 ✅
- GET session 详情 → 数据完整（session + turn） ✅
- CLOSE_WAIT 计数 → 0 ✅
