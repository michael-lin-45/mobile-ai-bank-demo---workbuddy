### A.2 trace 耗时畸大（2373098ms）+ TTFT=0 根因与双保险修复

- **现象**：trace 列表「耗时」=2373.1s，Span 瀑布图 E2E/L0/L1 = 2373098ms（两者是同一存储值 `durationMs=2373098`，仅单位展示不同）；TTFT=0ms 且明显错误。
- **根因（纠错后定论）**：非单位换算错、非 1000×。真正原因是 **WebFlux 未启用 Reactor 自动上下文传播** → 手写 INTERNAL span（`DomainRouter`/`ObsDocumentRetriever`/`ObsReRanker`）`startSpan()` 取到的 `Context.current()` 是上一个请求残留上下文 → traceId 跨请求泄漏、duration 虚高、intent 串标。HTTP 入口 `SERVER` span 本就是 javaagent 自动埋点（无需改）；L0/L1/L2 业务 span 必须手写，无法改自动埋点。
- **双保险修复**：
  - **治未病（上游）**：新增 `OtelContextConfig`（`@Configuration` + 静态块 `Hooks.enableAutomaticContextPropagation()`），激活 Reactor↔OTel 桥接（由 javaagent 运行期提供），手写 span 的 parent 自此正确，不再跨请求合并。详见 A.4。
  - **治已病（存量数据兜底）**：新增 `SpanDurationNormalizer`（`observability/backend/.../service/SpanDurationNormalizer.java`，`normalize(List)` 在 `OtlpParserService.parseTraces` 写库前对同 trace 的 span 重算，`:232` 调用）：以子树真实 `CLIENT` span 的墙钟包络（`min(start)/max(end)`）重算被污染畸大的 `durationMs`/`end_time`。`CLIENT` span 由 agent 自动埋点、时间基准正确，包络可信。
  - **TTFT 修正**：`TraceQueryService.computeTTFT`（`:425`）原 `if (ttft>60000) return 0L` 的坏钳制会输出误导性假 0；改为 `return null`（`:467`，注释明示 `fake 0ms would mislead the UI; return null so the frontend shows "-"`），前端显示「—」。
- **提交状态**：`SpanDurationNormalizer` + `OtlpParserService` 接入 + `TraceQueryService` TTFT 改 `null` → commit **`cac889b`**（已提交 `feat/demo-v4`）。

### A.3 主程序 LLM endpoint 路径去写死 /v1

- **背景**：Spring AI 1.1.2 `OpenAiApi$Builder` 默认 `completionsPath` 写死 `/v1/chat/completions`；主程序 `ModelConfig` 两处建 `OpenAiApi` 只设 `baseUrl` 未覆盖 → 最终 URL = baseUrl + "/v1/chat/completions"。很多 base_url 已以 `/v1` 结尾（会重复成 `/v1/v1`），且 `/v2`、`/v3` 形式写死 `/v1` 不适配。

- **测试**：`ModelConfigPathTest` 7 用例（无版本/v1/v2/v3/null/大写/尾部空白），工程师 7/7、QA 独立重跑 7/7。

### A.5 start-all.ps1 ECJ 残片规避 + 核心系统(8080)启动超时诊断

- **现象**：`start-all.ps1` 跑到 4/6 核心系统 `Waiting http://127.0.0.1:8080/actuator/health ... (55/60)` 超时；本地 8080 无 LISTEN；脚本 `Stop-AllAndExit` 清理全部端口。
- **真因**：`core.log`（仓库根）报 `java.lang.Error: Unresolved compilation problems: The import io.opentelemetry.api cannot be resolved` @ `ObsChatModel.java:6` → Spring 上下文起不来。机制：Eclipse/ECJ 在 IDE 编译 `ObsChatModel` 时 classpath 缺 `opentelemetry-api`，生成「带错误的 class」残留进 `target/classes`；`mvnw package` 增量编译误判 up-to-date 未重编，直接 repackage 进 jar；运行时一加载即崩（javac 会直接 BUILD FAILURE，不会生成此类 class）。
- **构建硬化（commit `51612d0`）**：`scripts/start-all.ps1`：
  - 两处 `mvnw.cmd package` → `mvnw.cmd clean package`（根治 IDE/ECJ 残片，先删 `target/` 强制重编）。
  - 新增 `Assert-NoEcjErrorClasses`（global 函数）：构建后扫描 `target/classes` 是否含 ECJ 错误标记 `Unresolved compilation`，命中即 `Stop-AllAndExit` 并给清理提示。
  - 在 backend/core JAR 检查后各调一次（预防 `clean` + 检测 `扫描` 双保险）。
- **运行时修复（随构建硬化一并生效）**：删 `pom.xml` 重复的 test `opentelemetry-api` 1.49.0 声明、compile `opentelemetry-api` 对齐 1.49.0；`mvn.cmd -o clean package -DskipTests` 用 javac 强制重编覆盖 ECJ 残留 → BUILD SUCCESS（92 源文件）。`nohup java -jar` 拉起 core，`/actuator/health` 返回 200 `{"status":"UP"}`，且打印 `baseUrl=.../v2` 印证 A.3 的 /v1 修复对 /v2 生效。
- **QA 验证**：语法 `SYNTAX_OK`；注入伪造 ECJ 错误 class → 函数命中并 `exit 1`、干净目录放行 `exit 0`；完整性/无回归 → 判定 **NoOne** 可交付。
- **非阻塞建议（待办）**：脚本全局 `$ErrorActionPreference=SilentlyContinue` 会抑制 `Write-Error` 显示，命中 ECJ 残片时用户只见清理日志不见原因；可改 `Write-Warning`/`Write-Host` 提升可读。
